# Neuronpedia label checker

An automated version of the Nov 12, 2026 held-out validation of
Neuronpedia's auto-generated feature labels (Gemma-2-2B, Gemma Scope
16k SAEs). The pilot and scale-up showed 59 of 200 labels passing a
held-out test written from the label itself. This tool runs the same
loop end to end: take a label, write a fresh test for it, score the
test against the feature, and — for labels that fail — probe *why*
they failed and tag the failure mechanism.

## Quick start

You need two free API keys and about two minutes:

```bash
git clone https://github.com/dcgleason/neuronpedia-label-validation
cd neuronpedia-label-validation/checker
cp .env.example .env
```

Open `.env` and paste in both keys (see `.env.example` for where to
get each; the free tiers are fine):

- `NEURONPEDIA_API_KEY` — from [neuronpedia.org](https://www.neuronpedia.org)
  (account / API section). Required: it scores the activations.
- `ANTHROPIC_API_KEY` — from [console.anthropic.com](https://console.anthropic.com).
  Needed to generate prompts with Claude; skip it if you plan to use
  `--prompts-in` with prompts written elsewhere.

Then verify the Anthropic key and run the checker:

```bash
python3 generate.py --check-key

# The calibration set: 40 pilot labels with pre-written prompts.
python3 run_checker.py --labels calib-labels.json \
    --prompts-in calibration-prompts-in.json \
    --rewrites-in calibration-rewrites-in.json --out runs/my-run
```

Two conveniences worth knowing: if a key is missing and you run in an
interactive terminal, the tools prompt you to paste it (hidden input)
and offer to save it into `.env` for next time; and real environment
variables (`export NEURONPEDIA_API_KEY=...`) always take precedence
over `.env` values.

## The pipeline

1. **Labels in.** A labels file (`[{layer, source, index, label}]`),
   or a fresh random sample drawn from the public feature API.
2. **Prompts generated** (see "Prompt generation modes" below):
   2 should-fire + 2 near-miss sentences per label, plain ordinary
   prose, each near-miss changing exactly one variable, plus a
   registered PASS/FAIL prediction and a one-line basis per test.
3. **Prompts locked.** Written to `<out>-prompts-locked.json` with a
   SHA-256 hash file before any scoring, same discipline as the pilot.
4. **Scored** through the Neuronpedia activation API. Pass rule (the
   pilot rule): `min(should-fire) > max(near-miss)`. Scores are cached
   on disk (`cache/`) so a prompt is never paid for twice; runs are
   resumable.
5. **Failures diagnosed.** Mechanism checks (one variable at a time)
   tag each failure as `word-form`, `register`, `displaced-theme`,
   `document-bound`, or `unresolved`. The register check (v3) prefers
   **style probes**: sentences that imitate the style/register of the
   feature's own stored examples on a neutral topic, supplied per test
   with `--style-in` (or generated through the rewrite function when
   none are supplied); rewrites of the should-fires and a fixed
   template probe remain as fallbacks.
6. **Report out.** `<out>-results.json` and `<out>-summary.md` in the
   scaleup-summary format, with a mechanism tag on every failure.

## Files

| File | What it does |
|---|---|
| `envkeys.py` | API-key handling for a fresh clone: reads keys from the environment or a `.env` file, and prompts (hidden paste) on interactive terminals. Keys are never printed or logged. |
| `score.py` | Activation scorer with disk cache, rate limiting (documented limit: 1000 requests / 60 min), and a hard stop on 401/403. Credentials: `NEURONPEDIA_API_KEY` via `envkeys.py`; inside Muse's own environment, the `custom.neuronpedia` connector credential is a fallback. |
| `generate.py` | Prompt generation: the TEMPLATE, the Anthropic API plug-in (mode a), `--prompts-in` loading (mode b), schema validation, the register-rewrite helper, and the `--check-key` self-test. |
| `mechanisms.py` | The failure checks, v3 (`theme_count` topical, `keyword_test`, `surface_mining` with the dominant-function-word exception, `register_swap` style-probe-first, `length_test` neutral-only evidence) and the `classify()` decision table. Thresholds are named constants at the top of the file. |
| `mechanisms_v2.py` | The v2 mechanism sorter, preserved verbatim for the record (see Calibration). |
| `mechanisms_v1.py` | The v1 mechanism sorter, preserved verbatim for the record (see Calibration). |
| `run_checker.py` | The CLI that runs the whole pipeline. |
| `calibrate.py` | Compares a checker run against human ground-truth verdicts (agreement %, confusion counts, disagreement list, mechanism-tag accuracy). |

## Running it

```bash
# With prompts generated externally (mode b):
python3 run_checker.py --labels labels.json --prompts-in prompts.json --out runs/my-run

# Standalone, prompts generated by the Anthropic API (mode a):
python3 run_checker.py --labels labels.json --out runs/my-run

# Or sample fresh features (labels fetched from the public API):
python3 run_checker.py --sample 60 --layers 6,12,18 --seed 42 --out runs/sample-run

# With style probes for the register check (mechanisms v3):
python3 run_checker.py --labels calib-labels.json \
    --prompts-in calibration-prompts-in.json \
    --style-in style-probes.json --out runs/my-run

# Calibrate a run against ground truth:
python3 calibrate.py --checker-results runs/my-run-results.json \
    --ground-truth ../results-raw.json --out CALIBRATION.md
```

## Prompt generation modes

- **Mode (a) — Anthropic API (standalone).** Used automatically when
  `ANTHROPIC_API_KEY` is available (environment or `.env`) and no
  `--prompts-in` is given. See the next section.
- **Mode (b) — `--prompts-in <file>`.** Prompts written externally
  (e.g. by Muse in-session) in the scaleup-prompts schema
  (`{"tests": [{test, layer, source, index, label, should_fire,
  near_miss, predicted, basis}]}`). Loaded and validated through the
  same validation path as mode (a).
- **Neither** → the run stops with a message saying exactly which of
  the two to supply.

## Adding an Anthropic API key (the plug-in point)

Mode (a) is fully implemented in `generate.py` (`_anthropic_messages`):
it POSTs to `https://api.anthropic.com/v1/messages` with the standard
headers (`x-api-key`, `anthropic-version: 2023-06-01`), sends the
generation TEMPLATE at temperature 0.2, and parses + validates the JSON
reply through the same `validate_test` path as mode (b). The key is
resolved at call time by `envkeys.py`. It is never logged and never
included in error messages (errors carry only the API's own status and
error text), and it is written to disk only into a `.env` file you
explicitly approved when prompted. The register-rewrite helper used
by the `register_swap` mechanism check goes through the same call.

To enable it, supply the key either way (only the key is required;
`CHECKER_MODEL` is optional):

```bash
# Option 1: a .env file next to the scripts (see Quick start)
cp .env.example .env        # then paste ANTHROPIC_API_KEY into it

# Option 2: environment variables
export ANTHROPIC_API_KEY="sk-ant-..."        # your key, from console.anthropic.com
export CHECKER_MODEL="claude-sonnet-5-5"     # optional; this is the default
```

On an interactive terminal you can also just run the tools with no
key set: you will be prompted to paste it (hidden input), with an
offer to save it into `.env` for next time.

Default model: `claude-sonnet-5-5` (current Sonnet, Sep 2026;
`claude-sonnet-4-5` retires 2026-11-30). Override with `CHECKER_MODEL`
to use another Claude model, e.g. `claude-haiku-5-5` for cheaper runs.

Then verify the plug-in end to end with one command:

```bash
python3 generate.py --check-key
```

Expected output with a working key:

```
ANTHROPIC_API_KEY: present
API check: success (model claude-sonnet-5-5 responded)
```

`--check-key` makes one minimal API call (max_tokens=16) and prints
only whether the key is present and whether the call succeeded — never
the key. Run it on the machine where the checker will run: this
sandbox VM's outbound traffic goes through an egress proxy that does
not pass api.anthropic.com, so the success path can only be exercised
where direct API access works.

Two robustness details: if a model rejects the `temperature`
parameter (some newer models do), the call is retried once without it;
and connection failures (DNS, timeout, reset) surface as a clean
"request failed" error, not a traceback.

## Calibration

The checker was calibrated against the 40 hand-tested pilot labels
(fresh prompts, same pass rule, verdicts compared by feature index,
mechanism tags compared against the 17 hand-autopsied silent
features). Results, the disagreement list, and honest notes on where
the checker is weak: see `CALIBRATION.md`.

Mechanism sorter versions: that calibration ran sorter **v1**, whose
mechanism tags scored **2/17** against the hand autopsies — it
over-tagged `displaced-theme`, because its theme check matched label
words literally in the stored examples (v1 is preserved verbatim in
`mechanisms_v1.py`; its report is `CALIBRATION-V1.md`). Sorter **v2** (preserved in `mechanisms_v2.py`)
added topical (stemmed) theme counting, surface-form mining of the
stored examples, a topical-document length test, a register template
probe, and a decision table in which `displaced-theme` requires
positive evidence and `unresolved` is the default; it scored **4/17**
(see `CALIBRATION-V2.md`). `mechanisms.py` is now **v3**: register
evidence from style probes that imitate the feature's own examples,
the topical length document demoted to reporting-only (it was
tautological as evidence), an evidence-based `displaced-theme` test
with no theme-band gate, and a mining exception for dominant function
words.

- Mechanism accuracy, v1: 2/17 (see `CALIBRATION-V1.md`)
- Mechanism accuracy, v2: 4/17 (see `CALIBRATION-V2.md`)
- Mechanism accuracy, v3: 4/17 (see `CALIBRATION-V3.md`)

Smoke test on record: the four original pilot prompts for feature
1657 ("Tom") scored through `score.py` reproduce the pilot's recorded
values exactly (20.25 / 21.75 should-fire, 13.50 / 0.00 near-miss).
