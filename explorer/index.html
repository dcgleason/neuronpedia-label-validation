Neuronpedia label validation · Gemma-2-2B & Llama 3.1 8B

Do auto-generated feature labels survive held-out text?

Neuronpedia’s feature labels are written by an explainer model from a feature’s top-activating examples. They are never tested on fresh text. This study tests them: for each label, two positive prompts that should make the feature fire and two hard-negative prompts that should not, written and predicted in advance, then scored against the real feature. A label passes only if both positive prompts activate clearly above both hard negatives.

How the failures break down

Failure classes: No activation — neither positive prompt activated the feature at all. Partial — the feature fired, but weakly or on only one positive prompt. Hard negative outscored — a hard-negative prompt outscored every positive prompt.

Start with one feature

Gemma layer 12, feature 5158 is labeled “elements related to buttons in a UI or web interface.” On fresh text it scored 0.00 on “Click the blue button in the top right corner to submit the form” and 0.00 on “The download button appears once the file is ready.” Follow-up probes found why: the feature fires on the code token btn in HTML (activation 45.0) and not at all on the word “button” in ordinary prose (0.0). The label names a concept. The feature detects a string.

What the failures look like

Most failures are not random. The label describes a broad concept; the feature turns out to be something narrower and more mechanical. One example: a Gemma feature labeled as detecting UI buttons did not fire on ordinary prose about buttons, because it actually detects the code token btn. Across the features that never fired, the same shapes recur: word-form detectors, register detectors (obituary formulas, clinical-journal style, forum questions), and features bound to document structure rather than meaning.

Labels can be fixed. After the pilot, 21 failed labels were rewritten from the probe evidence and retested on fresh prompts: 15 of the 21 corrected labels passed, against 0 of 21 for the originals. That result is what Study 2 tests properly.

Study 2: can labels be made accurate?

A labeling bake-off on the same 60 Gemma layer-12 features, with the same held-out protocol for every method. Predictions are made per label, locked, and publicly committed before any scoring. Design published November 14, 2026; the run is planned for December 2026.

ABaseline — the current Neuronpedia label, fresh prompts
BFull-range examples — explainer sees stored examples across the activation range
CFeedback loop — the current label, revised against its own Study 1 failures
DNarrow-label instruction — the explainer is told to prefer narrow labels
ECareful human — a person writes the label from the same evidence (20 features)
FVerified selection — several candidate labels, the one that scores best on trigger texts ships

Pre-registered headline predictions: baseline passes at most 15% of the previously failed features; full-range examples at least 35%; the feedback loop at least 50%. If the feedback loop lands under 30%, the feedback claim is dead. Full design, prior-art scan, sample, and arm specifications are in the repository.

Method: prompts and predictions were drafted with the assistance of an AI research assistant and approved by Danny Gleason before locking. Pass rule: min(positive) > max(hard negative). All raw scores are in the repository.

Width control: the 65k-width Gemma arm was not run. Local scoring failed bridge validation against the Neuronpedia API, so the arm is recorded as a limitation and contributes no records to this explorer. See the bridge check results.

## Study 3: can the fix be systematized? Study 1 tested labels, autopsied the failures, and rewrote the correctable labels from the evidence: 15 of 21 corrected labels passed, where the originals passed 0 of 21. Where Study 2 compares ways of writing labels, Study 3 automates the checking and fixing loop itself. It is proposed, not yet run. For each label, the pipeline generates the test prompts, scores the feature, and computes the margin. For each failure, it gathers the same evidence the hand autopsies used — the feature's strongest stored examples, the exact tokens it fires on, and a few cheap checks (remove the keyword and retest, swap the register and keep the content, test at document length) — and sorts the failure by mechanism. Where the evidence states what the feature really responds to, the pipeline drafts a corrected label that says only that, then retests it on fresh prompts under the same locked protocol. Where the evidence states nothing, the feature is marked unresolved and no label is offered. No model judges any label at any stage; every verdict comes from the feature's own activations. The end product is a number next to each label: its margin, published as a trust score, so a reader can see how much a label was measured to be worth instead of a "No Scores" marker.
